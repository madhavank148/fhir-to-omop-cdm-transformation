NEW L3 DATA PRODUCT DESIGN PROPOSAL

FHIR to OMOP: an analytics-ready L3 product

FHIR stays our base. OMOP becomes an additional consumer data product on top of foundation, so analysts and AI agents can ask real questions without re-solving FHIR parsing and code-system differences on every query.

0Summary for decision makers

What

A new L3 product that exposes foundation data as an OMOP Common Data Model (v5.4): one person table, domain tables for conditions, drugs, measurements and visits, and standard concept IDs for every code.

Why

AI systems will ask open analytical questions. In FHIR each question needs JSON parsing, many joins, and hand-kept lists of codes across SNOMED, ICD-10, LOINC, CPT and local systems. OMOP does that work once, centrally.

How

Streams and tasks from foundation into a staging and mapping layer, a vocabulary reference layer (Athena), and OMOP tables. Landing, foundation and RQ are untouched.

Main risk

Local codes cannot map themselves. Coverage depends on curated mappings per submitter. We measure and report it rather than hide it.

The ask: agree to a first slice (Person, Observation Period, Visit, Condition, Measurement, Drug), name an owner for vocabulary and local-code mapping, and run a benchmark that compares AI answer accuracy on foundation against OMOP. See Plan and Decisions.

1The problem

Foundation holds correct, complete FHIR R4, but FHIR is built for exchange, not analysis. Take the question "How many patients aged 20 to 30 had an HbA1c above 9% last year?"

Many parses per question

Patient to Observation is a string reference. The test sits inside code.coding[], an array. The value may be in valueQuantity, a coded value, or a component.

Many code systems

Submitters send SNOMED, ICD-10, LOINC, CPT and local codes. The same lab can arrive under several, so each query needs a maintained list of codes.

No standard enrichment

No hierarchies ("any statin", "any diabetes"), no normalised units, no consistent visit types. Each consumer rebuilds these, differently.

It is doable in FHIR. The issue is cost and consistency: every analyst and AI agent pays that cost on every question, and different people get different answers.

2The idea

Add one more L3 product that does the hard work once. It reads foundation, standardises codes, and presents the data in the OMOP Common Data Model.

We are not replacing FHIR. Foundation stays the full-fidelity base. Every OMOP row keeps its original source code and a lineage pointer to the foundation resource.

3What OMOP is, in seven ideas

OMOP (the OHDSI Common Data Model) is an open community standard for observational health data, maintained by the OHDSI CDM Working Group. The documentation site lists v5.5 as current; the FHIR-to-OMOP guide targets v5.4, which is what we propose.

1. Person-centric

One PERSON row per patient. Everything else is a dated row pointing back to person_id.

2. Split by domain, not resource

Facts go to the table for what they are (condition, drug, procedure, measurement, observation, device), decided by the concept's domain. One FHIR Observation can become a Measurement or an Observation.

3. Standard vocabularies

Every term is a row in CONCEPT with an integer ID and a domain. Standards: SNOMED (conditions), RxNorm (drugs), LOINC (measurements), CVX (vaccines), UCUM (units).

4. Source to standard mapping

Codes such as ICD-10 map to standard concepts via CONCEPT_RELATIONSHIP ("Maps to"). Unmappable codes get concept 0; the row is kept.

5. Hierarchies

CONCEPT_ANCESTOR stores "is-a" relationships, so "any statin" or "any diabetes" is one join.

6. Three columns per fact

*_concept_id (standard, for analytics), *_source_value (original text), *_source_concept_id (original code as a concept). Plus *_type_concept_id for provenance.

7. Derived data

OBSERVATION_PERIOD (when the person is observable) is required by OHDSI tools and absent from FHIR. Eras (CONDITION_ERA, DRUG_ERA) roll repeated records into episodes.

5The same question in both models

"Patients aged 20 to 30 with an HbA1c above 9%." Illustrative SQL; FHIR-side column names follow our foundation pattern but were not run against production.

Foundation (FHIR) you maintain the code list 
SELECT DISTINCT p.RESOURCE_ID
FROM FOUNDATION.OBSERVATION o
JOIN FOUNDATION.PATIENT p
  ON REPLACE(o.FHIR_SUBJECT:reference::STRING,
             'urn:uuid:','') = p.RESOURCE_ID,
LATERAL FLATTEN(o.FHIR_CODE:coding) c
WHERE
  ( (c.value:system = 'http://loinc.org'
     AND c.value:code IN ('4548-4','17856-6',
                          '59261-8' /* ... */))
 OR (c.value:system = 'urn:local:lab'
     AND c.value:code IN ('A1C','HBA1C' /* ... */)) )
  AND o.FHIR_VALUEQUANTITY:value::FLOAT > 9
  -- units? % vs mmol/mol?
  AND DATEDIFF(year, p.FHIR_BIRTHDATE::DATE,
               CURRENT_DATE) BETWEEN 20 AND 30;
OMOP no parsing, no code list 
SELECT DISTINCT p.person_id
FROM measurement m
JOIN concept_ancestor ca
  ON ca.descendant_concept_id
     = m.measurement_concept_id
 AND ca.ancestor_concept_id = :hba1c_concept
JOIN person p USING (person_id)
WHERE m.value_as_number > 9
  AND m.unit_concept_id = :percent_concept
  AND YEAR(m.measurement_date) - p.year_of_birth
      BETWEEN 20 AND 30;

Local lab codes only appear here if they have been mapped. That mapping is done once, centrally, and measured by a coverage report.

6Architecture of the new product

Landing and foundation are context only. What is new sits to the right of foundation.

6.1 Schemas

Every OMOP row keeps *_source_value, *_source_concept_id and a lineage column holding the foundation RESOURCE_ID, so any fact traces back to full-fidelity FHIR.

6.2 Refresh flow (streams and tasks)

  1. Capture change set. Streams on every foundation table are copied into one change-log table in a single transaction. A stream's offset advances when its changes are consumed in a committed transaction, so this keeps a multi-stream product consistent and replayable.
  2. Latest version wins. Foundation is append-only and deduplicates on full content, so two versions of one resource can coexist. Keep the newest per resource_id.
  3. Resolve identity. Patient references become the person key from the existing identity logic; FHIR IDs become stable integer OMOP IDs through a crosswalk.
  4. Map to OMOP. Pick the best coding, look up the standard concept, route to the table for the concept's domain, keep source values.
  5. Upsert event tables. Replace the earlier OMOP row of the same resource so no fact is counted twice.
  6. Rebuild derived rows for affected persons: observation period and eras.
  7. Refresh coverage and quality reports.

6.5 Design points to state clearly

Events versus derived rows

A Condition maps to one row independent of anything else. OBSERVATION_PERIOD and eras depend on a person's whole history, so when anything about a person changes we recompute that person's derived rows.

Late-arriving data

A Condition can arrive before its Encounter. visit_occurrence_id is nullable; the person-level rebuild back-fills the link once the Encounter lands.

Stable integer IDs

OMOP keys are integers. A persistent crosswalk gives each FHIR resource ID a fixed integer so IDs do not change when data is replayed.

Cross-file references

Practitioner, Organization and Location references use identifier queries rather than direct IDs, so resolving them into PROVIDER and CARE_SITE needs an explicit step with orphan handling.

Field-level policy

  1. Always keep *_source_value, *_source_concept_id and a lineage column to foundation RESOURCE_ID.
  2. Never drop an unmapped row. Give it *_concept_id = 0 and report it.
  3. Type concept (*_type_concept_id) is set to the EHR provenance concept for all clinical rows.
  4. Dates. Derive the date from a FHIR datetime; leave *_datetime NULL when the source has no time of day.
  5. One OMOP row per FHIR resource_id (latest version wins).

Known information loss

The IG names four kinds of loss. We accept them, document them, and keep the full FHIR in foundation.

Loss typeMeaningExample here
FidelityA specific source term maps to a broader standard conceptA local lab code maps to a general measurement concept
InformationSource data has no OMOP fieldExact witness time of a medication administration
RelationshipLinks between records are split across tablesCondition evidence or basedOn links are not preserved
AccuracyOMOP needs data the source lacksDrug exposure end dates derived rather than observed

10How we prove the value

Run the same questions through an AI agent twice, once over foundation and once over OMOP, and compare accuracy, SQL complexity and human corrections.

  1. Pick 20 to 30 questions (the starter set is below; add real stakeholder questions).
  2. Write a reference SQL answer on OMOP for each, checked against a hand-verified sample.
  3. Run the agent over each model with only the semantic definitions each model provides.
  4. Score correct, partially correct or wrong, plus latency and number of joins.
  5. Separate mapping findings from modelling findings. A wrong answer caused by an unmapped local code is a mapping gap, not an OMOP failure.

Prerequisites before build

  1. Athena access. Register (free), choose vocabularies (SNOMED, ICD10CM, LOINC, RxNorm, CVX, UCUM, NDC, CPT4 if licensed, plus domain and class reference data) and download a release.
  2. CPT4 licensing. CPT is AMA-licensed; the Athena download fetches it with a UMLS licence key. Decide whether to proceed without it initially.
  3. Person-key contract. Agree the output of the existing identity logic (stable, integer-friendly key).
  4. Baseline run. Pick benchmark questions and run them on foundation first.
