NEW L3 PRODUCT

FHIR to OMOP: a new L3 data product

FHIR stays our base. OMOP becomes an analytics-ready product on top of foundation, so analysts and AI agents can ask real questions without re-solving FHIR parsing and code-system differences every time.

1. The problem

Our consumers will increasingly be AI systems, and they will ask open-ended analytical questions. Foundation holds correct, complete FHIR R4, but FHIR is built for exchange, not analysis. Take: "How many patients aged 20 to 30 had an HbA1c above 9% last year?"

Many parses per question

Patient to Observation is a string reference. The test is hidden in code.coding[], an array. The value may be in valueQuantity, a coded value, or a component.

Many code systems

Submitters send SNOMED, ICD-10, LOINC, CPT and local codes. The same lab can arrive under several, so every query needs a hand-maintained list of codes.

No standard enrichment

There are no hierarchies ("any statin", "any diabetes"), no normalised units, no consistent visit types. Each consumer rebuilds them, differently.

It is doable in FHIR. The point is cost and consistency: every analyst and every AI agent pays that cost on every question, and gives slightly different answers.

2. The idea

Add one more L3 product that does the hard work once. It reads foundation, standardises the codes, and presents the data in the OMOP Common Data Model.

We are not replacing FHIR. Foundation stays the full-fidelity base. Every OMOP row keeps its original source code and a lineage pointer to the foundation resource, so any fact can be traced back.

3. What OMOP is, in seven ideas

OMOP (the OHDSI Common Data Model) is an open community standard for observational health data. Its current documented version is 5.5; FHIR-to-OMOP guidance targets 5.4, which is what we propose.

1. Person-centric

One PERSON row per patient. Everything else is a dated row pointing back to person_id.

2. Split by domain, not resource

Facts go to the table for what they are (condition, drug, procedure, measurement, observation, device), decided by the concept's domain, not by the FHIR resource type. One FHIR Observation can become a Measurement or an Observation.

3. Standard vocabularies

Every term is a row in CONCEPT with an integer ID and a domain. Standards: SNOMED (conditions), RxNorm (drugs), LOINC (measurements), CVX (vaccines), UCUM (units).

4. Source to standard mapping

Codes like ICD-10 are mapped to standard concepts through CONCEPT_RELATIONSHIP ("Maps to"). Unmappable codes get concept 0; the row is kept.

5. Hierarchies

CONCEPT_ANCESTOR stores "is-a" relationships, so "any statin" or "any diabetes" is one join.

6. Three columns per fact

*_concept_id (standard, for analytics), *_source_value (original code text), *_source_concept_id (original code as a concept). Plus *_type_concept_id for provenance (EHR, claim, registry).

7. Derived data

OBSERVATION_PERIOD (when the person is observable) is required by OHDSI tools and does not exist in FHIR. Eras (CONDITION_ERA, DRUG_ERA) roll repeated records into episodes.

5. The same question in both models

"Patients aged 20 to 30 with an HbA1c above 9%." Illustrative SQL; column names on the FHIR side are indicative of our foundation pattern.

Foundation (FHIR) you maintain the code list 
SELECT DISTINCT p.RESOURCE_ID
FROM FOUNDATION.OBSERVATION o
JOIN FOUNDATION.PATIENT p
  ON REPLACE(o.FHIR_SUBJECT:reference::STRING,
             'urn:uuid:','') = p.RESOURCE_ID,
LATERAL FLATTEN(o.FHIR_CODE:coding) c
WHERE
  ( (c.value:system = 'http://loinc.org'
     AND c.value:code IN ('4548-4','17856-6',
                          '59261-8' /* ... */))
 OR (c.value:system = 'urn:local:lab'
     AND c.value:code IN ('A1C','HBA1C' /* ... */)) )
  AND o.FHIR_VALUEQUANTITY:value::FLOAT > 9
  -- units? % vs mmol/mol?
  AND DATEDIFF(year, p.FHIR_BIRTHDATE::DATE,
               CURRENT_DATE) BETWEEN 20 AND 30;
OMOP no parsing, no code list 
SELECT DISTINCT p.person_id
FROM measurement m
JOIN concept_ancestor ca
  ON ca.descendant_concept_id
     = m.measurement_concept_id
 AND ca.ancestor_concept_id = :hba1c_concept
JOIN person p USING (person_id)
WHERE m.value_as_number > 9
  AND m.unit_concept_id = :percent_concept
  AND YEAR(m.measurement_date) - p.year_of_birth
      BETWEEN 20 AND 30;

Local lab codes only appear in the OMOP answer if they have been mapped. That mapping is done once, centrally, and measured by a coverage report.

6. What we build

NEW Vocabulary layer

REF_VOCAB: Athena tables plus a curated SOURCE_TO_CONCEPT_MAP for local codes. Shared by any future product.

NEW Mapping logic

Latest-version resolution, identity and ID crosswalks, coding priority (standard system first, then curated local map, else concept 0), domain routing.

NEW OMOP CDM tables

First slice: PERSON, OBSERVATION_PERIOD, VISIT_OCCURRENCE, CONDITION_OCCURRENCE, MEASUREMENT, DRUG_EXPOSURE. Then procedures, observations, death, health-system tables, eras.

NEW Quality and coverage

Mapping coverage by domain and submitter, unmapped-code backlog, row-count reconciliation to foundation, OHDSI data-quality checks.

Two design points worth stating to the lead

Foundation holds two versions; OMOP holds one fact.

Because foundation is append-only and deduplicates on full content, an Observation that moves from preliminary to final exists twice. The L3 step keeps the latest version per resource_id and replaces the earlier OMOP row, so analytics never double-count. This needs a reliable version-ordering field (meta.lastUpdated if foundation keeps it; load timestamp as a weaker fallback).

Event rows and derived rows behave differently.

A Condition maps to one row independently of anything else. OBSERVATION_PERIOD and eras depend on a person's entire history, so when anything about a person changes we recompute that person's derived rows. This is the part that needs the most careful design.

8. Limits and risks, stated plainly

BIGGEST RISK Local codes

Athena cannot know what a submitter's local code means. Without a curated mapping those rows get concept 0 and are invisible to concept-based questions. Mitigation: coverage report from day one, prioritise by row volume, a mapping workflow per submitter.

BY DESIGN Lossy mapping

Not every FHIR field fits. The IG names fidelity, information, relationship and accuracy loss. Mitigation: mapping matrix, source values kept, lineage to foundation.

OWNERSHIP Vocabulary is a product

Loading, versioning and re-mapping on each release; CPT4 is AMA-licensed. Needs an owner and a licensing decision.

ENGINEERING Derived tables and ordering

Person-scoped recompute, late-arriving data, stable integer IDs across replays. Sized once we know data volume.

SCOPE Guide gaps

The IG does not map MedicationRequest, excludes claims, and targets CDM 5.4 and FHIR R5 (we use R4). We need our own rules for medication end dates.

VALUE No named consumer yet

The AI use case is the consumer. We propose a benchmark: the same questions on foundation vs OMOP, scored for accuracy.

Not a good idea if consumers need lossless FHIR semantics (keep using foundation), or if nobody can own the vocabulary and mapping work.
